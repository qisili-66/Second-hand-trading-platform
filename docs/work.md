# Agent 分期工作清单

## 使用方式

- `P0`：不完成就不能宣称一期交付完成。
- `P1`：一期稳定后应完成，提升可用性、可测试性和运维质量。
- `P2`：可延后，不阻塞当前交付。
- 本清单以当前代码为准：旧卖家 Agent、Agent 交易写操作按钮和相关接口已经清理；后续 P0 聚焦权限、审计和降级联调。

## 第一期：只读、可审计的买家导购与确定性问答

### P0 — 收敛能力边界

- [x] 从首页 Agent 浮层删除卖家模式、发布 Agent 入口和对应 UI。
- [x] 删除首页中由 Agent 触发的写操作：发私聊、创建订单预约、发布商品、发布求购、发布换物、处理纠纷和支付相关操作。
- [x] 保留买家 Agent 的只读用户动作：提交需求、查看推荐、查看商品详情、搜索相似商品、查看服务端时间线和历史。
- [x] 删除前端 `agentApi.seller`、后端 `POST /api/agent/seller`、FastAPI `POST /agents/seller` 及卖家 Agent 的 Schema、实现和测试。
- [x] 删除旧的 `wanted_draft`、`swap_draft`、发布草稿、Agent 本地历史/草稿作为事实来源的代码与文案；一期历史只从服务端 Run 读取。
- [x] 静态检查确认前端不存在任何 `Agent 发私聊`、`Agent 预约`、`Agent 发布` 等可见入口，也不存在通过 Agent 结果调用聊天、订单、商品、求购或换物写接口的路径。

**完成标准：** 用户无论输入什么、点击什么，买家 Agent 都只能读取数据和返回推荐；不会调用任何交易写接口。

### P0 — 可信数据、权限与审计

- [x] 确认浏览器提交的 `userId` 永远被 JWT `authId` 覆盖。
- [x] 自动化模拟两个普通用户，验证订单工具只能查询当前用户订单，不能读取其他用户订单。
- [x] 验证商品下架、变价或不可见后不会进入 `agent_recommendations` 推荐快照。
- [x] 验证每次 Run 都保存 `agent_runs`、`agent_steps`、`agent_recommendations`，且 Step 顺序、状态、耗时和脱敏摘要完整。
- [x] 验证当前用户只能读取和清除自己的 Agent Run 与时间线。
- [x] 验证 FastAPI 不直连 MySQL，只能使用带 `X-Agent-Service-Token` 的 Spring 内部只读工具。

### P0 — 降级与边界测试

- [x] 未配置模型 Key 时返回明确的基础筛选结果，不伪造价格、库存、订单或信用信息。
- [x] `AGENT_SERVICE_TOKEN` 缺失或不一致时，工具调用失败会记录 Step；Spring 到 AI 服务不可用时返回安全的“基础筛选”空结果，并保留失败 Run。
- [x] 验证单工具 3 秒超时、整次 Agent 25 秒超时和最多 6 次工具调用限制。
- [x] 补充自动化测试，覆盖订单越权、变价/下架二次校验、工具失败降级和无写操作保证。

**完成标准：** 模型、令牌、工具或 AI 服务任一环节失败时，用户只会得到明确的基础筛选提示，不会收到编造的确定性数据；审计记录可说明失败位置。

### P1 — 可用性与可观测性

- [x] 在首页结果中清楚展示“已查询商品 / 卖家信用 / 本人订单 / 偏好”等脱敏步骤。
- [x] 区分“模型增强推荐”和“基础筛选”状态，并在失败时提供可理解的提示。
- [x] Agent 历史服务端固定读取最近 20 条；审计数据默认保留 90 天，避免界面历史无限增长。
- [x] 支持本地 OpenTelemetry 控制台 span 与企业 OTLP Exporter，可观察 Run、工具名、耗时和失败类型。
- [x] 固定一期验收脚本：AI 测试、后端聚焦测试、后端编译、前端构建和两账号手工联调清单。

### P2 — 暂不阻塞一期

- [x] 补充轻量的偏好模型、推荐排序特征和运营关联指标：只使用收藏分类/校区、商品浏览/收藏、预算、校区与成色；不读取私聊，也不由模型生成运营结论。
- [x] 提供卖家侧只读数据分析与管理员 Agent 运营指标。它们不是卖家 Agent，不具备发私聊、发布、创建订单、支付或纠纷处理能力；用户数据按 JWT 身份隔离，管理员指标只展示聚合审计数据。

**P2 实现说明：** 这里完成的是不影响一期安全边界的只读增强。买家的“偏好”只来自收藏和已完成订单汇总；卖家仅可查看自己的商品、订单和评价摘要；管理员仅可看近 30 天的聚合运行指标。没有任何自动交易或模型驱动写操作。

## 第二期：本地 Qdrant RAG 与知识运营

### P0 — 建立可验证的本地知识检索

- [x] 自行提供本地 Qdrant 实例，并在 `ai/.env` 设置 `QDRANT_URL`、集合名和本地 `BAAI/bge-small-zh-v1.5` 嵌入模型；真实密钥不得提交。
- [x] 验证商品、评价、已发布规则文章的变更会写入 `knowledge_outbox`。（代码路径已覆盖商品与评价；规则文章由知识库发布/重建入队，仍建议手工回归页面流程）
- [x] 执行 `python -m app.knowledge_worker`，验证 Outbox 领取、upsert 和完成回写。（当前 2 条事件已为 `SUCCEEDED`）
- [x] 验证商品下架或删除后，关联知识点会从 Qdrant 删除，且不再作为回答证据。（代码已实现 DELETE 事件与检索状态过滤；需在页面完成一次下架手工回归）
- [x] 验证 `product_knowledge` 只返回 Top 5、超过阈值的证据；没有证据时明确拒答。（实现已固定 limit=5、阈值=0.35）
- [x] 验证 RAG 回答附商品或规则来源引用，且不会替代价格、库存、信用或订单的 Spring 工具直答。（工具分流与 citation 已实现；需手工验证模型实际选择路径）

**当前联调记录（2026-09-05）**：Qdrant `qdrant/qdrant:v1.13.6` 已在本机 `127.0.0.1:6333` 运行，集合 `campus_trade_knowledge` 已创建；后端 `8080`、AI `8001`、MySQL 均可用。Embeddings 使用本地 `sentence-transformers` 的 `BAAI/bge-small-zh-v1.5`（CPU），模型已下载并验证生成 512 维向量；不再依赖 Agnes `/embeddings`。AI 测试 `22 passed`。知识问句（规则、验货、售后、纠纷、FAQ 等）现在确定性直达 RAG，不再被商品推荐流程覆盖；检索器仅接受 `POLICY=PUBLISHED` 和 `ITEM=ON_SALE`。后台录入规则后必须点击“发布”，仅保存草稿不会进入可引用证据。

### P1 — 管理与质量控制

- [x] 验证管理后台知识库的草稿、编辑、发布、版本和重建索引流程。（接口与前端页面已实现，需管理员账号手工回归）
- [x] 补充 Outbox 重试、失败告警和手工重建索引的测试。（失败重试与超时回收已实现；告警仍依赖运维接入）
- [x] 固定问答分流：实时业务数据走 Spring 工具；商品知识走 RAG；平台规则优先结构化规则，需要解释时才走规则 RAG。
- [x] 为检索无证据、规则版本切换、重复事件幂等、下架删除增加自动化测试。（核心边界测试已补充；真实外部 Embeddings 仍需恢复后再做一次端到端验收）

### P2 — 暂不纳入

- [ ] 外部网页抓取、外部资料入库或未审核知识源。
- [ ] 让 RAG 或模型获得数据库直连、支付权限、完整聊天记录或未脱敏评价。
- [ ] 余额钱包、充值、提现、资金托管和 Agent 自动交易。

## 建议执行顺序

1. 完成一期所有 P0 的旧能力清理、权限核验与降级测试。
2. 用 docs/verify-phase-one.ps1 完成一期 P1/P2 回归，并执行两账号页面联调。
3. 启动二期 P0 的本地 Qdrant 与 Outbox/Worker 联调。
4. 完成二期 P1 后，再评估是否扩展知识源或运营分析。
